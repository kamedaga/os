`.artifacts/` was accidentally deleted after WSL cache exhaustion and was
regenerated by the user. Historical runtime profiles, measurements, probe

Preserve the regenerated rootfs; do not replace it with an old test image.

## Reproduced startup failure and fix

The regenerated image contains signed/pinned Void Epiphany 48.5_1 and
WebKitGTK 2.50.4_1. Launching `epiphany https://example.com` failed with
`libephymain.so` / `libephymisc.so` not found and exit status 127.
`readelf -d` shows `/usr/lib64/epiphany` as the executable and private
library RUNPATH, while the upstream package payload is in `/usr/lib/epiphany`.
Only the analogous WebKit private-directory alias had been staged.

`tools/stage_void_webkit.py` now creates both private-directory aliases:

- `/usr/lib64/epiphany -> ../lib/epiphany`
- `/usr/lib64/webkitgtk-6.0 -> ../lib/webkitgtk-6.0`

No upstream binary/source or desktop-wide library search path was changed.
The packaging source is already listed in `pack/pack.yaml` build inputs.
The ordinary overlay conversion must follow staging: pacgo consumes regular
`CAPABILITYOS_ROOTFS_SYMLINK` marker files, not host symlinks. The regenerated
manifest was checked to contain both aliases after that conversion.
`python3 tests/test_void_webkit_overlay.py` passes all three tests, including
repeat staging, private-library/extension lookup, and marker conversion.

The missing alias was also created through the running guest filesystem
(not a raw live disk edit), and guest `sync` completed. A fresh Epiphany
process (Linux PID 122 for this run) launched with `LD_LIBRARY_PATH` unset;
its Example Domain body was captured. The source/staged-overlay fix ensures
future rootfs regeneration includes the alias. No rootfs copy or rebuild was
performed during this recovery.

## 2560x1264 memory-pressure finding

The existing host-timestamped serial log records the first GPU backing
admission refusal at 15:49:37, followed by many refusals, GPU resource-create
`-ENOMEM` results, and `fd-process-clone` faults at 15:49:41 and 15:50:01.
The hosted Linux core has a fixed 256 MiB RAM pool independent of the VM's
4 GiB guest RAM. During these refusals, the core had only 6,013-9,283 free
4 KiB pages (about 23-36 MiB); the DRM admission policy deliberately retains
32 MiB for render clients. A request as small as one byte was rejected when
free RAM fell below the reserve. The first two refusal diagnostics counted
19 DRM files and 888-889 live handle references, but imported objects may be
counted more than once, so those bytes are not a physical-residency total.
This is concrete memory pressure, not proof that a particular site, cache, or
process leaked. The user saw an unresponsive DuckDuckGo tab afterward; the
exact causal sequence still needs a fresh run.

To leave 128 MiB of extra room for multi-tab, 2560x1264 rendering,
`userland/kobox2_adapter/host.h` raises only the hosted-core pool from 256
to 384 MiB. The 4 GiB QEMU setting, pachagpu device and display mode are
unchanged. The device and VM-memory unit tests pass, and `pacgo build
userland gpud --force --no-rootfs` rebuilt `sandbox.elf` successfully.
This was initially a source/artifact-only change. It was subsequently deployed
as described below; do not report long-run stability from the short first
post-restart sample.

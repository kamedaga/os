# カーネル開発規約

カーネルを変更する人・エージェントと、その変更をレビューする人の共通規約です。
カーネルの設計・実装上の規約は、このファイルを唯一の正本とします。
README、エージェント向け指示、PR テンプレートには参照を置き、規約本文を複製しません。
作業開始時とレビュー時に読み、変更が下記の条件を満たすことを確認してください。

個別のリファクタリング計画や実装方式は、この規約とは分けて扱います。
文書は変更判断を拘束し、機械的に判定できる不変条件は、可能な限りコードとテストで
拘束してください。規約に書いたことだけで、検査が実装されたとは扱いません。

## カーネルに置く理由

実装前に、必要な特権・保護境界・資源管理の責任を示し、なぜ userland ではなく
カーネルが担当するのか説明してください。実装が楽になることは理由になりません。
サービス固有の方針や互換処理を、便宜のためにカーネルへ持ち込まないでください。

## コメントには why を残す

コードから読める「何をしているか」ではなく、次の変更者が安全に判断するための
「なぜこの制約・順序・処理が必要か」を、該当コードの直近に書いてください。
すべての行にコメントを要求するものではありません。

特に次の境界には、根拠となる不変条件と、破った場合に起きる問題を書いてください。

- ロックの取得順序、解放位置、ロック外で呼ぶコールバック。
- 所有権の移動、参照の公開、最後の参照の消滅、資源の回収・再利用。
- 並行実行や割り込みに対して、安全性を保つための制約。
- ハードウェア上の制約、回避策、一見重複している検査やコピー。

性能を理由に変更する場合も、既存の安全条件をどう維持するか説明してください。
変更に伴い理由が変わったコメントは更新し、成立しなくなったコメントは残しません。
レビューではコメントの有無だけでなく、理由が実装・検査・テストと一致するか確認します。

## 境界と責任

- モジュールと API ごとに、担当する責任、入力の前提、保証する結果、失敗条件を
  明確にしてください。呼び出し側に内部の制約や処理を重複させないでください。
- 意味や有効範囲の異なる値・資源を、区別せず扱わないでください。
  名前、型、API など、誤用を防げる適切な手段で区別してください。
- 保護境界を越えて受け取る値と参照は、利用前に検証してください。
  検証後に状態が変わり得る場合は、利用時まで安全性を維持する方法も定めてください。
- ABI を変更する場合は、変更の正当な理由と、呼び出し側への影響を説明してください。

## 所有権と寿命

- 資源ごとに、所有者、借用者、参照の有効期間、回収の責任者を API とコードで
  明らかにしてください。解放しないことで寿命問題を隠してはいけません。
- 資源の公開、所有権の移動、撤去・回収の条件を定めてください。
  参照先を置き換えたことだけを、古い資源を回収してよい根拠にしないでください。
- 途中で失敗する処理は、残る状態と資源の扱いを定めてください。
  巻き戻す場合も、変更を残す場合も、呼び出し側が結果を判断できるようにしてください。

言語や型が保証する範囲と、実装・実行時検査・テストで保証する範囲を区別してください。

## 並行実行と同期

- 共有状態について、読み書きする主体と、アクセスを安全にする同期方法を
  明確にしてください。ロックを使う場合は、保護する状態と取得順序を定めてください。
- 待機やコールバックなど、処理を中断したり別の処理へ入ったりする箇所では、
  保持中の資源と実行条件を確認してください。割り込みや再入も考慮します。
- 同期の範囲や方式を変える場合は、競合する経路と状態の公開順序を確認してください。
  同期を減らしたことや処理が短くなったこと自体は、安全性の根拠になりません。
- 待ち合わせでは、完了条件と進行を保証する条件を説明してください。
  長い待機や排他区間が必要な場合は、その理由と他の処理への影響を明示してください。

## 不変条件と検証

- 守るべき不変条件は、可能な限り API、型、検査、テストに反映してください。
  コメントや文書に書くだけで保証したとは扱わないでください。
- 検査を追加・変更する場合は、正常な状態を通すだけでなく、違反を検出できることも
  確認してください。必要な保証を機械化できない場合は、理由と確認方法を説明してください。
- 変更の影響に応じて、通常経路、境界条件、失敗経路、競合経路を検証してください。
  ビルドや単体テストだけで確認できない性質は、適切な実行環境で確認してください。
- 検証した条件、実行内容、結果、未確認の範囲を記録してください。
  性能改善は同条件の変更前後を比較し、測定値と推測を区別してください。

ビルドと起動の手順は [ビルドガイド](../pacha_docs/build.md) を参照してください。

## レビューと完了条件

変更の説明には、目的と範囲、カーネルが担当する理由、維持・変更する不変条件、
それを保証する方法、検証結果を含めてください。

レビューでは、次の条件を満たすことを確認します。

1. 変更対象の境界、責任、寿命、同期条件が明確である。
2. 守るべき不変条件が実装と検証に反映されている。
3. why コメントが現在の実装と一致している。
4. 影響に応じた検証が通り、残る制約や未確認事項が明示されている。

既存コード全体を一度に書き換えることは要求しません。ただし、変更対象に残る規約との
不一致は理由を説明し、「既存コードだから」という理由で新しい逸脱を追加しないでください。
新しい仕組みの定義だけを追加しても、対象経路が実際に使い、必要な検証が通るまでは
その移行を完了したと扱わないでください。
